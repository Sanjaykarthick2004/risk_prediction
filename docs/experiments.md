# Experiments

All numbers below are **actual output** from running this application's own training
endpoints against the bundled **SYNTHETIC DEMONSTRATION DATA** — a running-athletes-only
dataset, 10,000 rows, generated by `app/ml/data_loader.generate_synthetic_dataset`
(`random_state=42`), 80/20 stratified split (8,000 train / 2,000 test). They are reproducible
by re-running the same endpoints, but must not be cited as real sports-science findings — the
underlying data is synthetic and the effect sizes are modest by design (the synthetic target
includes substantial random noise specifically so the pipeline isn't trivially "solved").

The dataset's `injury_next_7_days` base rate is a naturally-imbalanced ~23.7% positive (not
resampled to force 50/50 — see [methodology.md](methodology.md)), so SMOTE is applied to the
training data. **SMOTE is applied fresh inside every cross-validation fold** (via an imblearn
`Pipeline`), never once before splitting into folds — resampling first and then K-folding the
already-resampled set would let synthetic minority samples leak between a fold's train and
validation partitions, inflating CV scores in a way that doesn't reflect real generalization.
This was caught and fixed during development (see the git history / PR description) after the
larger, properly-imbalanced dataset exposed it — CV F1 had been reading ~0.82 while genuine
held-out test F1 was ~0.11.

## Experiment 1 — Baseline Model Comparison
`POST /api/training/train`

| Model | Accuracy | Precision | Recall | F1 | Specificity | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|---|---|
| Logistic Regression | 0.6285 | 0.3295 | 0.5485 | 0.4117 | 0.6533 | 0.6368 | 0.3749 |
| Decision Tree | 0.6335 | 0.2543 | 0.2827 | 0.2677 | 0.7425 | 0.5126 | 0.2419 |
| Random Forest | 0.7545 | 0.4000 | 0.0717 | 0.1216 | 0.9666 | 0.6044 | 0.3242 |
| SVM | 0.6135 | 0.2752 | 0.3861 | 0.3213 | 0.6841 | 0.5545 | 0.2735 |
| Gradient Boosting | 0.7585 | 0.4384 | 0.0675 | 0.1170 | 0.9731 | 0.6231 | 0.3509 |
| XGBoost (default) | 0.7580 | 0.4306 | 0.0654 | 0.1136 | 0.9731 | 0.6013 | 0.3305 |

SVM is trained on a stratified 4,000-row subsample of the SMOTE-balanced training set for
runtime reasons (kernel SVMs scale very poorly past a few thousand rows); every model is still
evaluated on the identical 2,000-row held-out test set (see `app/ml/train_models.py:MAX_SVM_TRAIN_SIZE`).

**RQ2**: On this data, tree-based models (Random Forest, Gradient Boosting, XGBoost) reach the
highest accuracy and specificity but very low recall — with a 23.7% positive base rate, a model
that leans toward predicting "no injury" scores well on accuracy while missing most true
positive cases. Logistic Regression has the best F1 and recall of the six, a reminder that
accuracy alone is a misleading metric for imbalanced classification — this is exactly the
justification for reporting F1/ROC-AUC/PR-AUC/specificity together rather than accuracy alone.

## Experiment 2 — Default vs. Optimized XGBoost
`POST /api/training/optimize` (RandomizedSearchCV, 30 iterations, 5-fold stratified CV,
scoring=F1, SMOTE applied fresh inside each fold)

| | Accuracy | Precision | Recall | F1 | Specificity | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|---|---|
| Default XGBoost | 0.7580 | 0.4306 | 0.0654 | 0.1136 | 0.9731 | 0.6013 | 0.3305 |
| Optimized XGBoost | 0.7580 | 0.4742 | **0.1941** | **0.2754** | 0.9332 | **0.6328** | **0.3695** |

Best hyperparameters found: `n_estimators=180, max_depth=5, learning_rate=0.0110,
subsample=0.842, colsample_bytree=0.909, min_child_weight=3, gamma=0.994, reg_alpha=1.423,
reg_lambda=1.580`.

Leak-free 5-fold CV on the optimized model (original, unbalanced training split, SMOTE inside
each fold): accuracy 0.740±0.016, precision 0.397±0.065, recall 0.174±0.017, F1 0.241±0.025,
ROC-AUC 0.630±0.020, PR-AUC (avg. precision) 0.340±0.031 — consistent with the held-out test
numbers above, which is exactly what a trustworthy CV estimate should look like.

Training time for the full optimize run (default fit + 30-iteration randomized search + 5-fold
CV report + artifact persistence): ~80 seconds on a normal laptop CPU.

**RQ2 / H2**: hyperparameter optimization more than doubles recall (0.065 → 0.194) and F1
(0.114 → 0.275) over the default configuration, at a modest cost in specificity — a genuine,
meaningful improvement (unlike an earlier, leaky-CV version of this experiment where "optimized"
actually scored *worse* than default on the real test set, a symptom of the CV leakage bug
above). This is a modest but honestly-reported result: the model is still far from solving
prediction on this noisy synthetic target, which is by design.

## Experiment 3 — Modality Ablation
`POST /api/training/ablation` — a default (non-optimized) XGBoost retrained from scratch on
each cumulative modality subset (M3/M4 are alternate single-modality additions to M2, not a
strictly nested chain — see `app/ml/multimodal_fusion.ABLATION_CONFIGS`).

| Configuration | Modalities | F1 | Recall | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|
| M1 | Demographic | 0.0638 | 0.0359 | 0.4944 | 0.2414 |
| M2 | + Training | 0.0406 | 0.0211 | 0.5237 | 0.2710 |
| M3 | + Recovery (instead of physiological) | 0.0041 | 0.0021 | 0.5120 | 0.2470 |
| M4 | + Physiological (instead of recovery) | 0.0204 | 0.0105 | 0.5140 | 0.2543 |
| M5 | + Physiological + Recovery + Lifestyle | 0.0363 | 0.0190 | 0.5270 | 0.2664 |
| **M6** | **All six modalities incl. Injury History** | **0.1136** | 0.0654 | **0.6013** | **0.3305** |

**RQ3 / H1**: M1-M5 (which all exclude injury history) perform close to chance (ROC-AUC
~0.49-0.53); M6 (adding injury history) is a clear, large jump on every metric. This is
consistent with how the synthetic target was constructed — `previous_injury` and `injury_count`
carry the largest coefficients in the latent-risk formula (see
`app/ml/data_loader._generate_target`) — so the ablation study is behaving exactly as the data
was designed to demonstrate: injury history is the single most informative modality here, and
no other modality subset is a substitute for it. A real dataset would need to be checked for
whether this holds, rather than assumed from this demonstration.

## Experiment 4 — Global SHAP Analysis
`GET /api/explainability/global` — mean absolute SHAP value per feature over an 800-row sample
of the test set (`settings.shap_global_sample_size`), computed from the actual persisted
`shap.TreeExplainer`. Results change whenever the model is retrained; inspect the live endpoint
(or the Explainability page) for the current top features rather than a frozen snapshot here.
As of the run behind the numbers above, the top features were `injury_count`,
`speed_work_sessions`, and `fatigue_score` — consistent with the ablation result that injury
history dominates, plus a running-specific training signal (speed work volume).

## Experiment 5 — Individual SHAP Explanation
`POST /api/predictions` returns `top_risk_factors` / `protective_factors` for that one athlete,
and `GET /api/explainability/{prediction_id}/waterfall` returns every feature's contribution
sorted by magnitude — all computed on demand from the real preprocessed input and the real
model, never fabricated or looked up from a table.

## Interpretation Notes
- SHAP values describe how a feature moved the *model's own prediction* for that input — the
  application always phrases this as "contributed to the model's prediction," never as a claim
  that the feature caused an injury (see [methodology.md](methodology.md)).
- These are demonstration-scale results (10,000 synthetic running-athlete rows, one train/test
  split). A real research submission would need a real longitudinal injury dataset and repeated
  cross-validation before drawing sports-science conclusions.
- Performance is modest across the board (ROC-AUC 0.5-0.63), and that is reported honestly
  rather than adjusted to look better — see `docs/project_overview.md`'s viva-answer section for
  how to explain this if asked "why isn't the accuracy higher?": the target is a noisy synthetic
  simulation by design, not a solved classification problem.
